Extending the Weapon Animation System

The Animator template is a convention, not a cage. There are three levels of extension, and most of what people want needs no C# at all.

The naming contract

Everything the runtime touches is addressed by name. Keep these names and the runtime keeps working, whatever else you add to the graph.

Layers

Index Name Blending
0 Base locomotion
1 Actions Override, weight 1

States — Base: Idle, Walk, Sprint, Slide, Wallrun, SwimIdle, SwimForward, SwimBackward, SwimUp, SwimDown. Actions: None (default, no motion), Equip, Fire, FireADS, Reload, ReloadEmpty, Inspect, Holster.

Slide and Wallrun hang off Any State (with Can Transition To Self off) rather than being threaded into the Idle→Walk→Sprint chain, because either can begin from any point in it. Each has three exits — back to Sprint, Walk or Idle — so ending a slide into a sprint doesn't blend through the idle pose.

Sprint, Slide and Wallrun additionally require IsADS to be false, and each has an extra exit back to Walk on IsADS becoming true: these poses take the hands off the sights and would fight the procedural ADS pose. If you have authored an aimed sprint or slide, delete those IsADS conditions in your copy of the controller.

The five swim states also hang off Any State, on IsSwimming plus a SwimDirection equality test, so changing direction needs no state-to-state transitions. They are not gated on IsADS — see the integration matrix for why.

Parameters — Speed (float), IsSprinting, IsSliding, IsWallrunning, IsSwimming, IsADS, IsReloading (bools), SwimDirection (int: 0 idle, 1 forward, 2 backward, 3 up, 4 down), ReloadSpeed, EquipSpeed, HolsterSpeed (floats, bound as per-state speed multipliers).

All of it lives in one place in code: AFPS_WeaponAnimatorContract.

Warning

Never use Animator triggers in a weapon graph. Switching weapons re-activates the model, which rebinds the Animator and clears its parameters — a trigger set on that frame is silently dropped, so the animation you most need (the draw) is the one most likely to go missing. The shipped runtime uses Play/CrossFade with hashed state IDs for exactly this reason. Drive your own states the same way, or from bool/float parameters.

Level 1 — extend the graph (no code)

Duplicate WeaponAnimatorTemplate.controller, add whatever you like — blend trees for directional walk, a sub-state machine for a multi-stage reload, additive layers — then base your weapon's override controller on your copy instead of the shipped one. Keep the contract names above and every built-in behaviour keeps working.

The inspector notices that you are on a non-shipped controller and says so as an info message, not an error.

Regenerating the shipped template (Tools ▸ AFPS ▸ Generate Weapon Animator Template) rewrites only the shipped asset in place — it never touches your copy or any override controller, and it preserves asset GUIDs so existing weapons keep their slots.

Level 2 — call the playback API

// Any state on the Actions layer, entered exactly like the built-ins.
static readonly int MeleeHash = Animator.StringToHash("Melee");

myWeaponAnimator.PlayAction(MeleeHash, 0.05f);

PlayAction is guarded the same way the internal handlers are, so it is safe to call while the weapon is being switched away or dropped.

Also public: PlayInspect(), HasClip(slot), ClipLength(slot), HolsterDuration, Animator, and a Has…Clip property per slot.

Level 3 — subclass

Every event handler is protected virtual:

public class MyWeaponAnimator : AFPS_WeaponAnimator
{
    protected override void HandleFireEmitted(FireWeaponBase fireScript, bool released)
    {
        base.HandleFireEmitted(fireScript, released);   // keep the shipped fire clip
        if (fireScript is ProjectileFire)
            PlayAction(GrenadeThrowHash, 0.05f);
    }
}

Overridable: HandleFireEmitted, HandleEquipStarted, HandleDeEquipStarted, HandleReloadStateChanged. The custom inspector applies to subclasses too, so you keep the setup button, slot list and validation for free.

Recipe: per-pool reload clips

Out of the box one designated ammo pool drives the reload clip. To animate a second pool (an underbarrel launcher, say) differently:

  1. Add a LauncherReload state to your duplicated controller, on the Actions layer, returning to None on exit time.
  2. Subclass and route the second pool:
static readonly int LauncherReloadHash = Animator.StringToHash("LauncherReload");

protected override void HandleReloadStateChanged(AFPS_WeaponAmmo pool, bool started)
{
    // The designated pool keeps the shipped behaviour.
    base.HandleReloadStateChanged(pool, started);

    if (pool != launcherPool || !started)
        return;

    PlayAction(LauncherReloadHash, 0.1f);
}

Assign launcherPool from GetComponents<AFPS_WeaponAmmo>() in Awake, and speed-sync it yourself from pool.ReloadDuration if the clip lengths differ.

Adding an Inspect key

The asset deliberately ships no Inspect action — adding one to AFPS_PlayerActions would force every existing project to merge an input asset change for a cosmetic feature. If you add an action named exactly Inspect to your own copy of the input asset, AFPS_WeaponAnimator finds it by name when the weapon is equipped and subscribes to it automatically. Nothing else to wire.

Events from clips

AFPS_WeaponAnimationEventReceiver forwards AnimEvent("Key") to a keyed AudioClip + UnityEvent pair, and AnimSFX(clip) plays an AudioClip passed directly in the event's Object field. Both are cosmetic-only by design — see the warning in Quick Start.
