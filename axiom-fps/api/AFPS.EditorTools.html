Namespace AFPS.EditorTools

Classes

AFPS_ADSEditor

Adds the edit-mode ADS preview, the structural validation report and a play-mode state readout above the normal ADS inspector.

Derives from NaughtyInspector rather than Editor on purpose: NaughtyAttributes registers itself for every UnityEngine.Object, so a plain Editor here would silently drop every BoxGroup/ShowIf/Required on ADS.

AFPS_ADSPreviewOverlay

Scene view overlay for a running ADS preview. It exists because the preview outlives the selection: the moment you select anything other than the ADS component — a light, the aim point, a piece of level geometry — the inspector panel with the Stop button is gone, and the preview is still running with the cameras still zoomed. This gives it a home that doesn't depend on what's selected.

Shows itself only while a preview is active, and hides again when it stops.

AFPS_ADSPreviewSession

Drives the edit-mode ADS preview: stages a throwaway copy of a weapon under the scene's AFPS_WeaponSystem, poses it through AFPS_ADSPose, and drives the real main/weapon camera FOVs — which makes the GAME VIEW a true ADS render (the same two-camera composite as play mode, rather than a simulation of it).

Nothing authored is mutated. The staged weapon is a plain clone flagged HideFlags.DontSave, so it can never be serialized into a scene or applied back to a prefab. The camera FOVs are the only writes to real components; they're cached and restored on every teardown path, and temporarily reverted around a scene save so a save taken mid-preview can't bake the aimed FOV.

The preview stops (rather than trying to survive) on domain reload, play mode, scene change and editor quit — cheaper to re-toggle than to make cross-reload state correct.

AFPS_ADSValidation

Checks the structural assumptions the ADS aimed pose is built on. None of these produce an error at runtime — they all just make the sight quietly fail to land where the designer expects, which is the whole reason they're worth surfacing in the inspector.

The aimed pose collapses to weapon.localPosition = -adsPoint.localPosition with identity rotation, which parks the aim point exactly on the weapon system's origin. Everything below is a precondition of that identity holding.

Split into weapon-level and rig-level checks: a weapon prefab on its own can be checked for the first set, but the rig set needs a scene with a player in it.

AFPS_ADSValidationWindow

Project-wide ADS setup audit. The per-weapon inspector only tells you about the weapon you happen to be looking at; this catches the weapons nobody re-checked after a rig change — which is the way these break in practice, since none of them produce a runtime error.

Deliberately NOT an alignment report: the aimed sight position is fixed by the hierarchy (the aim point is parked on the weapon system's origin), so there is no per-weapon offset to measure. What varies, and what this checks, is whether each weapon still satisfies the structural preconditions that identity depends on.
