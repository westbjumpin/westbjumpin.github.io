Movement Arms Animation

The movement arms are the shared first-person arm rig used for climbing, ledge hangs, mantles, slides, crouching, running and swimming — the animations that read as the player's hands touching the world rather than holding a weapon. They are independent of whichever weapon is equipped, and independent of the per-weapon arms that come with an animated weapon rig (see Weapon Animation).

AFPS_ArmsController drives them, and it works the same way the weapon animator does: one generated template controller, an override controller whose named slots you drop clips into, hashed IDs, no triggers, and continuous poses polled from the player's movement state rather than pushed in by callers.

Upgrading is opt-in

If your project uses the shipped Arms.controller, nothing changes. The component detects that the assigned controller isn't contract-shaped and runs in legacy mode — the original string parameters and triggers, byte-for-byte the behaviour you had before. Migrate when you want to.

To migrate:

  1. Run Tools ▸ AFPS ▸ Generate Arms Animator Template once per project.
  2. Select the object with AFPS_ArmsController (the weapon-system root) and press Set Up Arms Animations. That creates an override controller from the template and assigns it to the arms Animator.
  3. Drag your existing arm clips into the named slots.

Arms.controller is left untouched, so reassigning it reverts you at any time.

Slots

Poses — continuous, polled from movement state, and looping:

Slot Plays while
Idle default resting pose
Walk Speed above 0.2 m/s
Run sprinting
Crouch crouched
Slide sliding
Wallrun wallrunning
Climb / Ladder climbing a wall or a ladder — ladders reuse the climb reach, as they always have
Ledge Grab hanging from a ledge
Swim Idle / Forward / Backward / Up / Down swimming; direction from input, exactly as for weapons

One-shots — played once and returning to rest:

Slot Plays when
Slide Start the movement state enters Sliding
Mantle the movement state enters Mantle, or Mantle() is called
Grab Grab() is called — by AFPS_InteractionSystem on pickup and interaction

Only Grab genuinely needs a caller: no movement state implies "the player just picked something up". Slide Start and Mantle are now derived from the state changing, so they no longer depend on AFPS_Movement remembering to call in.

What the refactor fixes

  • Dropped one-shots. Grab and SlideStart were Animator triggers. Showing the arms re-activates the GameObject, which rebinds the Animator and clears its parameters — a trigger set on that frame was silently discarded. Only Mantle had a hand-written workaround. The clip-slot path uses CrossFade with hashed IDs and holds any one-shot requested while the arms are hidden until they are back, so all three survive.
  • No string lookups per frame. Everything is a pre-hashed ID from AFPS_ArmsAnimatorContract, and unchanged parameters are never re-sent.
  • One source of truth for movement. The arms and the weapon read the same AFPS_MovementAnimationSampler snapshot, so they cannot disagree about whether the player is swimming, climbing or sprinting.
  • Empty slots never pop. As with weapons, a pose whose slot has no clip is never entered — entering an empty state with Write Defaults on snaps the rig to its bind pose.

Arms visibility

Unchanged in either mode. The arms are shown when the equipped weapon's Use Arms is on, and forced visible during climb, ledge hang, and for mantleArmsDuration after a mantle. MovementArmsForced exposes that forced window.

What an animated weapon actually keys off, though, is SharedArmsVisible — are the shared arms on screen right now, for any reason. AFPS_WeaponAnimator hides the weapon rig's own arm meshes for exactly as long as that is true, which is what stops the player seeing four arms. The forced flag alone was not enough: it is only one of the reasons the shared arms can be showing, so a weapon with Use Arms on drew both sets, and the weapon's arms came back a frame late on the way out.

Extending

Same contract rules as the weapon system. Duplicate ArmsAnimatorTemplate.controller, add what you like, keep the state and parameter names, and base your override controller on your copy. PlayAction(hash, fade) crossfades any state you add to the Actions layer.

Warning

Never use Animator triggers in the arms graph, for the reason above: the arms object is switched on and off constantly as weapons change.

States — Base: Idle, Walk, Run, Crouch, Slide, Wallrun, Climb, LedgeGrab, SwimIdle, SwimForward, SwimBackward, SwimUp, SwimDown. Actions: None (default, no motion), SlideStart, Mantle, Grab.

Parameters — Speed (float); IsSprinting, IsCrouching, IsSliding, IsWallrunning, IsClimbing, IsLedgeGrabbing, IsSwimming (bools); SwimDirection (int, 0 idle / 1 forward / 2 backward / 3 up / 4 down — the same values the weapon contract uses).

Troubleshooting

The arms don't animate after migrating. The template must be generated before the setup button can build an override controller from it. Check the validation box on the component.

A pose never plays. Its slot is empty, so the state is deliberately never entered. Fill it, or turn off Gate Locomotion To Filled Slots if you put the motion on the state directly in a duplicated controller.

The grab animation still gets dropped. You are in legacy mode — the inspector says so. That is the trigger bug; migrating fixes it.

Four arms during a climb. That is the weapon side: see Weapon Animation troubleshooting.
